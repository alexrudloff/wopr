## The extraction trap

Parse `HttpApiEndpoint.<method>("<name>", <Prefix>Paths.<key>)` across `groups/*.ts`, resolving each
`export const <Prefix>Paths` map. **Those maps mix three value forms**, and handling only one silently drops whole
group files:

| form | example | file |
|---|---|---|
| plain quoted string | `list: "/file"` | `file.ts`, `global.ts`, `experimental.ts` |
| template literal | `` status: `${root}/status` `` | `session.ts` |
| bare alias | `list: root` | `session.ts` |

A parser that resolves only `<Prefix>Paths` references and template literals reported 65 and dropped
`experimental.ts`, `file.ts`, `global.ts`. A second attempt that handled quoted strings still reported 108 and dropped
`config.ts`, `project.ts`, `provider.ts`, `question.ts`, `permission.ts`, `project-copy.ts`, `control-plane.ts`.

**The generator's guard is the deliverable, not the parser:** abort when the resolved count is below the raw
`HttpApiEndpoint.` occurrence count. That check is what would have caught both failures.

## Why no test guards the inventory

Two rounds of review rejected the proposed tests as the banned categories, correctly. A test over a committed JSON
file turns red when you edit the JSON and stays green when you delete a route from `serve.go` — it cannot observe
whether wopr mounts anything. The inventory's value is that it makes `docs/site/docs/server.md` *true*, not that it
fails. Any future proposal to re-add such a test should be refused on this record.
