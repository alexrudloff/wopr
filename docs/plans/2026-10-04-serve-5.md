## Decisions

### §Q1 — the todo list is derived from the transcript, never stored

**Decision: `GET /session/{id}/todo` reads the transcript and returns the items from the newest `todowrite` tool result's `Details`. No in-memory todo store exists anywhere. The same items also reach the tool part's `state.metadata.todos` on the transcript path, not only on the SSE path.**

The deciding fact is that a session is a file and the server is not. `sessionTodo` already resolves a **disk-only** session (`serve_handlers.go:411`) and `sessionMessages` already serves one (`:569-579`); an in-memory map answers `[]` for exactly the sessions those two handlers answer for. A phone reconnecting after a restart would show an empty todo panel against a conversation that visibly has todos in it. The plan's own phrase is "serve `/todo` from the latest `todowrite` result" (`plan:200-201`) — *latest*, not *current*, which is a transcript read.

The cost is real, and is why the reader is bounded rather than complete. The metadata survives JSON (`agent/tool_execution.go:420` → `ai/messages.go:150` → `agent/message_json.go:183`, sidecar §3) but comes back as `map[string]any`, so the reader marshals and unmarshals into `todowrite.Todo` and never type-asserts. The read reuses `tailEntries(rec.Path, maxLimit)` (`serve_read.go:420`) at `maxLimit` = 200 and takes the **last** match, mirroring `sessionMessages`'s file-then-live precedence (`serve_handlers.go:568-586`) so the two handlers cannot disagree about one session.

**The transcript-side surface is a second edit, not a consequence of the first.** `entriesToMessages` builds every tool part's `state` from `{"status","output"}` in three places (`serve_handlers.go:779-783`, `:812`, `:841`) and nothing in the serve package read `tr.Details` before this slice, so the SSE `toolSnapshot` fix alone leaves `GET /session/{id}/message` showing a todo part with no todos. That route is a **recovery surface**, not a convenience one: the client has no replay and recovers by re-fetching history (`plan:162-163`). Hence file #7's scope and the second half of DoD 5.

### §Q2 — the question store: one bounded map, ids from a time-seeded counter

**Decision: `Server` gains one field, `questions questionStore`, and `questionStore` is `struct { mu sync.Mutex; m map[string]*pendingQuestion }` defined in `serve_question.go` (file #8). `mu` is a plain `sync.Mutex`, not the server's existing `sseConnections atomic.Int64` (`serve.go:27`) — that one counts connections and is the only atomic on `Server` today. The id is `"q" + decimal(add(1))` off a `sync/atomic.Uint64` seeded once with `time.Now().UnixMilli()`. Each entry holds the session id, the `askuser.Question`, and a buffered `chan askuser.Answer` of capacity 1.**

The store is on the `Server` because `GET /question` is **not** session-scoped on the client (`plan:144`), so there is nowhere else for a server-wide list. Lifetime is the tool call: created when the asker is invoked, deleted before it returns on every path including the errors, so a finished question is not answerable twice.

**The answer-once window is one critical section.** Each of `reply` and `reject` takes `mu`, finds the entry, deletes it, and takes its channel out under the **same** lock acquisition, then sends on the channel after unlocking. Two concurrent replies to one id therefore yield one winner and one 404, and the asker sees exactly one `Answer`; without the single critical section the loser's send would block forever, because capacity 1 is already taken by the winner and nobody reads again. This is a non-obvious concurrency invariant, so it is stated in the field's comment, per `AGENTS.md`.

The counter is clock-seeded rather than zero-based for one reason — a client holding `q1` from before a restart could otherwise reply to an unrelated new `q1`. One `UnixMilli()` removes that class for one line and keeps ids short, ordered and debuggable in a log. Randomness buys nothing: answering a question is not a privilege on a server that already runs tools for anyone who can reach the port (`plan:210-212`).

The brief for a bounded store is met without an eviction policy, and the reason is the `ask_user` execution mode rather than the run rule. `askuser.Tool.ExecutionMode()` returns `agent.ToolModeSequential` (`askuser.go:68`), and the agent loop runs a whole batch sequentially when any call in it targets a sequential tool (`agent/tool_execution.go:52-53`, `:58-63`; the default is parallel, set at `agent/agent.go:615`). Two `ask_user` calls in one batch therefore execute one after another and cannot both be blocked. Per session the count is one as well: the host's run slot is held for the whole run by `PromptContent` (`coding/host/host.go:233-243`) and `PromptContentWait` (`:255-267`) — **not** `Session.Prompt` (`:216-223`), which serve never calls — so a session has at most one run in flight and a run at most one blocked `ask_user`. **No cap constant is added.** If an entry count ever needs one, that belongs to the slice that has a reason to want it.

### §Q3 — `GET /question` with nothing pending is `200 []`

**Decision: always `200`, always an array, never `404` and never `null`.**

The client polls this to populate a list. `404` is its signal for "host gone" (`plan:147-149`), so spending it on "you have no questions" makes an empty inbox indistinguishable from a dead server — the exact false signal the 501-over-404 decision at `BACKLOG.md:308-316` exists to prevent. `[]` not `null`, because `listSessions` (`:200`) and `sessionStatus` (`:404`) both emit non-nil empty slices and a decoder should not have to distinguish missing from null.

Reply and reject answer **200** with no body, matching `sessionAbort` (`serve_prompt.go:169-176`) rather than `prompt_async`'s 204 (`plan:129-130`). 204 is the plan's marker for "accepted, results arrive on the stream"; a question answer's result is the assistant turn that follows it, so 200 is the honest answer for an endpoint that is not itself doing the work.

### §Q4 — an aborted run kills the question, and a pending question holds the run slot

**Decision: the asker selects on `ctx.Done()`; whichever fires first wins. Cancellation deletes the entry, returns `ctx.Err()`, and emits `question.rejected`.**

`askuser.Tool.Execute` already turns a cancelled context into `errors.New("question was aborted")` and a returned error into a failed tool result (`askuser.go:141-143`), so the model is told the question died rather than handed a fabricated answer. That existing behaviour is why the store needs no cleanup goroutine of its own.

**The cancel a phone can reach is `POST /session/{id}/abort`** (`serve_prompt.go:174` → `Session.Abort`, `coding/host/host.go:312`), which cancels the run context the asker is selecting on. `Session.Close` (`:324`) also cancels, by way of the same run teardown, but **no HTTP handler calls it**: `DELETE /session/{id}` is the 501 stub (`serve.go:61`) and `cmd/wopr/serve.go` has no shutdown path. So `abort` is the path DoD 10 exercises, and it is the only one a client can take.

Emitting `question.rejected` on the cancellation path is the decision most likely to be contested, so the reasoning: without it the phone renders a question card that can never be answered and never goes away, because the client has no replay and no expiry (`plan:162-163`). With it, the card resolves. A reply arriving after the entry is gone is **404**, not a silent success — the phone learns the question is gone instead of watching the model proceed on a reply that never landed.

**A pending question holds the run slot, and the resulting 409 is correct.** The slot is held for the whole run (`host.go:193`, `:233-243`, `:300-306`), so a run parked in `ask_user` holds it and every further `prompt_async` on that session answers **409** for as long as the phone deliberates. That is the invariant doing its job — one run per session is what keeps a phone and a script from interleaving turns (`plan:357-359`) — but it is the first thing a reviewer files as a bug, so DoD 11 asserts it as intended behaviour.

### §Q5 — `/file/content`: an 8 MiB cap, and binary is refused

**Decision: `maxFileContentBytes = 8 << 20`; over it is **413**; a file with a NUL byte in its first 8 KiB or any invalid UTF-8 is **415**; success is **200** `{"content": string}` and nothing else.**

The cap takes the **number** from `maxInlinedImageBytes = 8 << 20` (`serve_read.go:465`) but not its meaning. That constant is a *cumulative budget over one tail read* — initialised once before the loop and decremented per resolved record (`serve_read.go:437`, `:442-443`) — so it bounds one transcript's total inlined payload, not any single blob. 8 MiB is still the right number for a single file, on its own terms: it is below wopr's largest pinned transcript entry at 17 MiB (`session_large_line_test.go:33`, `plan:218-223`) and far above one decoded phone photo. A separate constant name is used because a constant named for one concern must not silently serve the other.

**413, not truncation.** A truncated body served as a complete file is a lie the client cannot detect: it has no length to compare against, since the cap is the server's and not the file's. 413 with the real size in the error body tells it something actionable. `plan:218-223` reserves 16 MiB for *request* bodies, which is the wrong number for a response — bounding a read-only endpoint by the request cap would mean the largest file it can serve is the largest request it can accept, a coincidence and not a reason.

**415 for binary, with the ceiling named.** `writeJSON` (`serve_handlers.go:33-39`) runs `json.Encoder.Encode`, which substitutes U+FFFD for every invalid UTF-8 byte; a binary served that way is silently corrupted and looks fine. Measured on this tree's toolchain: invalid UTF-8 comes back as U+FFFD, and a NUL byte round-trips **byte-exact**. So the corruption rationale justifies the invalid-UTF-8 half of the predicate only, and the NUL half is refused for its own reason — NUL marks a file as non-text to every other consumer in the tree, so serving it as a string hands the client text in name only. Both halves are one predicate and one status either way. Base64 in a second field is the alternative and is not taken because the plan names no body contract here (`plan:139`) and there is no Swift in this repo to check — guessing at an encoding is what `plan:222-223` warns against. **If the manual client check (against `grapeot/opencode_ios_client` at `2d0e7bd`, which is a client-side check outside this repo's gates) shows the app wants base64 for images, this becomes one extra field and the 415 branch goes away.**

The status mapping reuses `listFiles`'s existing mapping verbatim (`serve_handlers.go:428-448`), because `resolveInRoot` returns the same three sentinels (`serve_dto.go:200-204`) and two handlers mapping them differently is drift nobody would notice.

### §Q6 — `todowrite` is on by default in every mode, and `wopr serve` has no way to turn it off

**Decision: registered in `CreateAllTools`, **not** named in `optInBuiltinToolNames`, and added to `agentToolNames` at `main.go:565`. Off in TUI/print/json via `--exclude-tools todowrite` or `--tools`, which already exist. On `wopr serve` it is unconditionally active and cannot be disabled.**

`BACKLOG.md:616-617` says this "changes what the model can do in **every** mode", and `plan:362-363` adds the "not only remote" half; together they are the whole argument, because a default the user must discover is not a default. All three consumers are covered — serve picks it up automatically because `Host.Start` passes no `ActiveBuiltinTools` (`coding/host/host.go:101-104`), while TUI/print/json need the one-token addition because `activeBuiltin` there is explicit and `BuiltinToolActive` (`tools.go:98-108`) honours it over the opt-in list (sidecar §8). Missing that token is the failure mode where the tool exists, passes every test, and is silently unavailable in the mode the developer actually uses.

**The CHANGELOG line says "active by default" and stops there.** `wopr serve` has its own flag parser accepting only `--port` and `--hostname` (`cmd/wopr/serve.go:52-56`, `:95-138`); any other option exits 2. `runServe` reads no `settings.DefaultTools`, no exclusion and no allow-list, and `host.StartOptions` (`coding/host/host.go:86-89`) carries only `Model` and `SessionDir`, so `Host.Start` has no field through which to pass an exclusion. A line claiming `--exclude-tools todowrite` disables it would be false for the one mode this slice exists to serve. Adding that field would be a 13th file and a knob nobody asked for; it is recorded as an open question instead.

It goes in `CreateAllTools` (`tools.go:163`), not `CreateCodingTools` (`tools.go:134`), because the latter is the **shared** set three subagent paths build from (`coding/session_task.go:339` and two siblings). A subagent with a todo list writes todos nothing reads. `askuser` is kept out of subagents for the same class of reason (`askuser.go:1-4`).

Three conventions in that file decide the placement, and all three are named in file #2's scope. `CreateAllTools` **splices** rather than appends — `coding[:2]`, `PowerShellTool`, `coding[2:]` (`:163-169`) — so `todowrite` is appended to the trailing `coding[2:]` group; appending to a different index would silently move `powershell`' position in the registry. `builtinToolNames` is documented as being in `CreateAllTools` order (`:77-78`), so the new name goes last, after `ls`. And `DefaultToolGuidelines` enumerates every built-in by hand (`:175-187`), so `PromptGuidelines` on the new schema would never reach the builders that call that function; the tool therefore either gets an entry in that list or carries no `PromptGuidelines` at all.

Opt-in was the alternative and loses on one fact: the tool is the only producer of both client surfaces, so opt-in means the todo panel is empty on every session that did not pass a flag. Unlike `ask_user`, `todowrite` never blocks on a human, so enabling it costs schema bytes and nothing else.

One behavioral test is added, which is what `plan:362-363` requires and what `AGENTS.md`'s "do not add tests by default" permits: this is a new agent capability and the regression is a tool that silently accepts a malformed list or an out-of-set status value.

### §Q7 — the permission route is registered under a different wildcard name

**Decision: `POST /session/{id}/permissions/{permissionID}`, not the plan's `POST /session/{id}/permissions/{id}`. The wire path is byte-identical.**

Go's `ServeMux` rejects a pattern that reuses a wildcard name (`net/http/pattern.go:130`, `:176-179`) and `HandleFunc` panics on the error, so the plan's spelling verbatim aborts `serve.New` and takes down **all thirty** routes. Reproduced in sidecar §2, not reasoned about.

The panic is reached only when `use121` is false (`net/http/server.go:2927-2932`). Under `GODEBUG=httpmuxgo121=1` the 1.21 mux stores the pattern literally, with no wildcards at all (`net/http/servemux121.go`), so both spellings register successfully and both then answer 404 to a real request. Either way the plan's spelling does not work and the corrected one does, which is why the correction is safe without knowing which behaviour is in force — verified under both settings in sidecar §2.

This is a correction to the plan, not a design choice, and it is the one place where following the plan literally breaks the slice.

### §Q8 — `Todo` mirrors the client's decoder, and `Parse` constrains the values

**Decision: `todowrite.Todo` is the client's `TodoItem` verbatim — `id`, `content`, `status`, `priority` (`plan:179`) — and `Parse` rejects a `status` outside `pending` / `in_progress` / `completed` / `cancelled` and a `priority` outside `high` / `medium` / `low`.**

Field **names** are the part of `plan:179` that is a server-side contract. The rest of that line — each field "has a decoder fallback" — is a fact about the client, not a constraint wopr can enforce or observe. Without a value check here, a model writing `status:"done"` round-trips faithfully into a todo the phone's panel cannot render, and DoD 6 as written passes for any string. The check is one `switch` in `Parse`, which is the shape `askuser.Parse` already uses for option counts and label lengths (`askuser.go:108-123`).

The two sets have different footing, and the difference is deliberate:

- `status` — opencode's four values. Constraining it is safe: an unrecognised status is a value the panel cannot draw, and rejecting it in `Parse` turns a silently unrenderable todo into a tool error the model can correct.
- `priority` — **provisional.** `plan:179` names the field and not its values, and zero `.swift` files exist in this tree, so `high`/`medium`/`low` is the working assumption, not a verified contract. It goes in the same `switch` because the alternative is worse — no check at all — and it is an open question below. If the manual client check disagrees, the fix is one line in the same `switch`.
