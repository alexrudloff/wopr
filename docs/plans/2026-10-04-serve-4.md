## Q1 — the byte bound

**Decision: replace the `chan []byte` subscriber channel with a mutex-guarded FIFO carrying an exact queued-byte counter, and take a byte budget in `Subscribe`.**

`Bus.Publish` already does the half that matters — it marshals once and hands the same `[]byte` to every subscriber. Its two doc comments **contradict each other** on what gets marshalled: `bus.go:8-9` says "Publish marshals Data exactly once", `bus.go:33-35` documents `json.Marshal(ev)`, and the code at `bus.go:44` sides with `:33-35`. serve-4 makes the code match `:8-9`, which is the last paragraph of this section. What is wrong with the queue itself is only this: `bus.go:59-64` blocks on `sub.ch <- payload`, and `bus.go:78` builds that channel with an **event count** (`make(chan []byte, buffer)`). The item already flagged it: `bus.go:41-42` says "Publish blocks on a full subscriber buffer. serve-4 replaces this with a byte-bounded buffer and a terminal drop event."

**Why the channel cannot be counted in bytes.** Tracking cumulative queued bytes on top of a buffered channel needs three properties that cannot coexist:

- The producer must know the byte total before deciding to enqueue, so the increment belongs under a lock.
- The send must not block while that lock is held, or a consumer that needs the same lock to decrement deadlocks against a full channel.
- Two producers must not both observe a free budget and both enqueue, or the "bound" is not a bound.

A buffered channel gives none of these: its occupancy is not observable, and the only way to decrement is to have the consumer take the lock the producer is not allowed to hold across the send. So the channel is replaced, not decorated.

**The shape.** One `sync.Mutex`, a `[]frame` FIFO, `queuedBytes int`, `bound int`, `dropped bool`, and a `ready chan struct{}` of capacity 1 used as a coalescing wakeup. `Push(name string, payload []byte) (dropped bool)` never blocks. `Next(ctx, timeout) (name string, payload []byte, terminal bool, err error)` pops under the lock, returns `err` on context end, and returns `terminal` once the queue is drained *after* a drop. The element is a pair, not a `[]byte`, because `ev.Data` alone carries no event name (see the `Publish` paragraph below):

```go
// frame is one queued SSE frame's two halves. Publish marshals Data only, so
// the event name cannot be recovered from the payload and must travel with it.
type frame struct {
	name    string
	payload []byte
}
```

Producers signal `ready` on push and on drop; the consumer never signals, because no producer ever waits. A push that lands between the consumer's unlock and its select leaves a token in the cap-1 channel, so there is no lost wakeup and no spurious stall. `Close` stays as it is — it removes the subscriber and closes `doneCh`, and must still not close the payload channel, for the two reasons already written at `bus.go:106-112`.

**The bound: `32 << 20` (32 MiB), declared as `2 × maxTailBytes`.**

`maxTailBytes = 16 << 20` (`serve_dto.go:118`) is the session **tail-read** window — `serve_read.go:418-424` walks back at most that many bytes to satisfy a client's `limit`. A budget of 2× it holds the largest pinned transcript entry (17 MiB, `internal/codingagent/session_large_line_test.go:33`, `const textBytes = 17 << 20`; plan:220-223) plus a second frame with room to spare, and it is derived from a constant already in the package rather than a number invented here. A budget below one maximum-size event is not a budget, it is drop-on-arrival — an image-heavy session would kill every connection the moment one entry arrived, which is the plan's own failure mode (plan:242-243) in miniature. The cost is 32 MiB of resident memory per **stalled** connection, and only stalled ones: a connection that drains never accumulates. That is bounded and independent of conversation length (plan:235-237). DoD 7 caps concurrency so the aggregate has a ceiling too.

**The byte bound counts `len(payload) + len(name)`.** The name is queued memory too — a 16-byte string header per frame regardless of whether the name's bytes are shared with the producer — so a bound that ignores it does not bound the queue. It costs one `+ len(name)` in the two places that touch the counter (`Push`'s increment and the oversized-frame branch), which is why the counter is a single local `n := len(name) + len(payload)` in `Push` rather than an expression repeated. Reachability is unchanged: the longest name is `message.part.updated` at 20 bytes, against a payload ceiling of 17 MiB and a bound of 32 MiB.

**One event larger than the bound: drop the subscriber and account it.** If `len(payload)+len(name) > bound`, no queue can honour the budget, so the only non-lying action is to mark the subscriber dropped and count the violation. This branch is unreachable with the derived 32 MiB against a 17 MiB maximum entry, so it is a guard, not a policy — and it is worth having because it is testable with one synthetic oversized frame. The code comment says so.

**On drop, the already-queued frames are still delivered, then the terminal frame.** Dropping the queue too would leave the client holding a partial message with no marker of where it stopped; delivering the prefix then the terminal keeps the client's view coherent and makes the drop detectable.

**The terminal frame is `event: session.error` + `data: {"error":…}`, then `data: [DONE]`, then close.** The plan requires a terminal event (plan:241-243) and a `[DONE]` sentinel (plan:121) but names no event for either. `session.error` is one of the 17 the client already switches on (plan:156), so it is received; an invented name could be silently dropped by a client that tolerates unknown events but nothing would surface. `sessionID` is `""` and the payload carries `{"error":{"name":"SSEDropped","message":"connection exceeded its 32MiB buffer"}}`. The subscriber builds this frame itself — the bus never sees it — which is why `terminal bool` on `Next` is enough.

**`Publish` marshals `Data`, queues it beside `Event.Type`, and returns an error.** Today `Publish` marshals the whole `Event` (`bus.go:44`) while its own contract at `bus.go:8-9` says it "marshals Data exactly once". serve-4 makes the code match the contract: `json.Marshal(ev.Data)`, once, and the subscribers queue those bytes **paired with `ev.Type`**. The pairing is mandatory, not stylistic: `ev.Data` is the payload alone, so a subscriber holding only `Data` bytes has no event name, cannot write `event:`, and hands every frame to the client untyped — DoD 4 is unachievable on a `[][]byte` queue. So `Publish` marshals once and pushes `frame{name: ev.Type, payload: payload}`, and `Next` returns the name alongside the bytes.

This is what lets the SSE handler write `event: <name>` + `data: <payload>` with no unmarshal anywhere. The rejected alternative was to keep marshalling the whole envelope and unwrap `Type` once at the frame writer: it puts `{"type":…,"session":…,"data":{…}}` where the client expects the payload, it costs one `json.Unmarshal` per event **per connection** on the hot path, and it leaves the subscriber's self-built terminal frame (built in the paragraph above, where the bus never sees it) constructed in a different shape from every other frame the queue carries. `Event.Type` is therefore the SSE event name, set by the producer; the bus never interprets it, and `bus.go:11`'s comment is updated to say so.

`Publish` returns `error`, which closes serve-1's recorded open item ("Publish cannot observe a json.Marshal failure", `BACKLOG.md:83-84`). The forwarder counts the failure and continues the run: every payload is a plain struct of strings and ints built by the mapper, so a marshal failure is a mapper bug, not a runtime condition, and losing one event beats tearing down every session's stream.

**Evidence.** `BenchmarkServeFanout` with `-benchmem`, in `coding/host/host_test.go`, over a fixture of at least 8,000 events and four subscribers whose readers stall long enough that an unbounded queue would exceed the declared bound by an order of magnitude (plan:266-271). A benchmark cannot assert, and AGENTS.md forbids change-detector shapes, so the two requirements split:

- `BenchmarkServeFanout` — allocation and byte evidence for the fan-out and the drop path. No assertions beyond `b.Fatal`.
- `TestServeFanoutDropsStalledSubscribers` — the assertion with teeth: all four subscribers receive the terminal drop frame. This is the check that a dropping implementation actually drops.

The existing `host_test.go:193` call `b.Subscribe(1)` changes to `b.Subscribe(1 << 20)`.

## Q2 — the prompt path, the run reservation, and abort

### The API, stated precisely

`Host.Prompt` blocks today: `host.go:130-137` takes `TryLock`, then `s.sess.Send` returns only after the run ends, and `defer s.run.Unlock()` holds the slot for the whole turn. So `prompt_async` cannot answer 204 immediately through it, and a goroutine cannot surface `ErrSessionBusy` synchronously. serve-4 replaces it with two methods that share one reservation:

- `PromptContent(ctx, []ai.UserContentBlock) error` — takes the same `run.TryLock`, returns `ErrSessionBusy` **synchronously**, and on success starts `SendContentWithPreflight` on a goroutine it owns. Answers 204 the moment the reservation lands. Everything after the reservation is reported on the SSE stream, which is opencode's own contract for an accepted prompt.
- `PromptContentWait(ctx, []ai.UserContentBlock) ([]agent.AgentMessage, error)` — same `TryLock`, blocks until the run settles. Backs `/message`.

The reservation is the contract: exactly one run per session, owned by `Host.Session`, released by whichever of the two paths finishes. `Prompt(ctx, text string)` stays as it is — serve-1 shipped it and `host_test.go:138,152,166` is its recorded proof of the run rule.

**The pre-`beginAgentRun` window, and why serve-4 needs no new plumbing for it.** `beginAgentRun` stores the run's cancel at `coding/session_run_state.go:100-101`, which happens inside `sendContent` (`coding/session.go:682`). Between the reservation and that assignment there is a window in which the session has a run slot and no cancel. RPC closes it with `promptPending` plus `promptWG` (`rpc.go:512-514`, `:670-686`) — but `promptPending` exists to feed `streaming()` at `rpc.go:513`, not the abort window, which `settlePrompt` closes with `promptWG.Wait()` at `rpc.go:549`. The flag's state also duplicates `cancel != nil`. serve-4 borrows neither: it owns a `context.CancelFunc` set at the reservation and cleared when the run settles.

`sendContent` already exposes the seam RPC uses. `SendContentWithPreflight` (`coding/session.go:646-650`) invokes `preflight` at `:678`, immediately **before** `beginAgentRun` at `:682` — that is the pre-`beginAgentRun` hook, already exported, already used by RPC at `rpc.go:672-676`. serve-4 passes `nil` for `preflight` (it has no response to write from inside the run) and relies on the owned cancel instead, which is strictly simpler: `context.WithCancel` over an already-cancelled parent yields an already-cancelled child, so a cancel delivered before `beginAgentRun` still stops the run.

**The trap, stated as an invariant on the new methods.** `prompt_async` answers 204 while the run continues, and `http.Request.Context()` is cancelled the moment the handler returns. Passing `r.Context()` into the run therefore kills the run the instant the response is written — a silent, total failure of the item's whole point, with a 204 in the log. Both methods must detach: `context.WithoutCancel(r.Context())` to keep request values, then `context.WithCancel` over it, owned by `Host.Session`. This is on the signature as a comment because the bug is invisible in review and obvious only at runtime.

### Abort

`Session.Abort` exists (`coding/session_run_state.go:85-88`): `RequestAbort` then `WaitForIdle`. serve-4 does not use the wait. `RequestAbort` (`:71-81`) unconditionally calls `AbortRetry()`, `AbortCompaction()` and `AbortBranchSummary()` at `:75-77`, and its nil-guard at `:78-80` covers **only** `cancel()` — so an abort on an idle session still reaches all three, and the only thing the guard withholds is the run cancel. serve-4's `/abort` is therefore:

1. `host.Session.Abort` fires the owned cancel if the reservation is outstanding, then calls `Inner().RequestAbort()`.
2. The handler answers **200**.

No wait, no timeout, no `ctx.Err()` path, and nothing to decide about a client that disconnects mid-abort. The cancel has already been delivered synchronously, which is the client's actual intent ("stop that session"); the drain happens in the background and the SSE `session.status` reports `idle` when it lands. Aborting an idle session is 200 — "stop nothing" is success. An unknown id is 404. Nothing else is a 5xx.

### `/message`

The body carries `parts` and the four structured fields the plan names (plan:128):

| Field | serve-4 behaviour |
|---|---|
| `parts` | sent. `type:"text"` → `ai.TextContent`; `type:"file"` → `ai.ImageContent` with the data URL split into mime and base64 |
| `model` | **applied** — resolve against `AvailableModels` and call `Inner().SetModel`, the same shape RPC uses at `rpc.go:771-782` (§Q5) |
| `system` | accepted, ignored |
| `format` | accepted, ignored |
| `agent` | accepted, ignored |

The three ignored fields are **not struct fields**. `json.Decode` silently ignores unknown keys, so a body struct that declares only `parts` and `model` accepts `system`, `format` and `agent` for free. One `ponytail:` comment names the ceiling and the upgrade path: a per-prompt system override, a JSON-schema-constrained retry loop (opencode's `StructuredOutputError` path is a feature), and runtime agent personas (serve-3's `/agent` returns a static four-name list at `serve_handlers.go:372-381`) are three different slices.

`SetModel` is a **session-wide, variadic** mutation, not a per-request one: `coding/session.go:827-829` says "swaps the active LLM model… The next Send uses the new provider/model", and `setModel` (`:839-862`) stores it, pushes it into the agent, appends the audit entry, and sets the thinking level. So `model` on `/message` changes the session's model for **every later prompt**. There is no per-request model in wopr, and pretending otherwise would be a lie in the API. It is safe here because the handler applies `model` **before** taking the reservation and answers 409 on a busy session, so serve never mutates the model mid-run.

The content route needed a new host method and this is it. `Inner()` (`host.go:121-126`) is documented as "the deliberate, documented escape hatch for the read surface; serve never calls **Send** on it" — serve-4 sends through `PromptContent`/`PromptContentWait`, never through `Inner()`, so **that doc comment does not change**. `Inner().SetModel` is not a send.

`directoryParam` is serve-3's, unchanged (`serve_handlers.go:60-71`): absent or matching is accepted, mismatched is 400. `prompt_async` and `message` both need it (plan:129, 136-137).

**The body cap.** plan:218-223 mandates `http.MaxBytesReader` on every body-carrying handler at 16 MiB. `/message` is the one new body-carrying handler and the one that ingests base64 images from an unauthenticated LAN peer, so it is the one where the cap matters. `maxBodyBytes = 16 << 20` already exists (`serve_dto.go:121`). serve-3's PATCH uses `io.LimitReader` (`serve_handlers.go:249`) and answers **400** on any decode error (`serve_handlers.go:249-252`); `/message` uses `http.MaxBytesReader` and answers **413**.

`http.MaxBytesReader` sets no status — it returns a `*http.MaxBytesError` from `Read`, and the handler must branch on it. So the status is produced here, and nothing else in this slice changes it:

```go
r.Body = http.MaxBytesReader(w, r.Body, maxBodyBytes)
if err := json.NewDecoder(r.Body).Decode(&body); err != nil {
	var tooLarge *http.MaxBytesError
	if errors.As(err, &tooLarge) {
		s.writeJSON(w, http.StatusRequestEntityTooLarge, errorDTO{Error: "request body too large"})
		return
	}
	s.writeJSON(w, http.StatusBadRequest, errorDTO{Error: "invalid body"})
	return
}
```

**Why 413 and not serve-3's 400.** serve-3's 400 is not an idiom chosen over 413; it is the only status `io.LimitReader` allows, because that primitive cannot tell a truncated body from malformed JSON and hands back one indistinguishable error. The plan names the stronger primitive (plan:218-223), and adopting `MaxBytesReader` while discarding the one error type it exists to produce would buy nothing over the `io.LimitReader` already in the tree — it would be a deviation with no observable difference. On the one endpoint that ingests base64 images from an unauthenticated LAN peer, "the photo is too big" and "the JSON is broken" are different client bugs and the client should be able to tell them apart. serve-3's PATCH is **not** retrofitted to 413; that is a separate cut and this slice leaves `serve_handlers.go:249` alone.

A body over the cap must still be **read past the limit** for the decode to fail at all — `MaxBytesReader` errors on the read that crosses the bound, so the branch fires mid-decode rather than at a length check. The table row above therefore covers every body at or over `maxBodyBytes`, not just bodies that fail to parse.

`/message` answers **200** with the finished `{info, parts}` message, because opencode's split is the reason the plan lists two endpoints and because `/prompt_async`'s 204 is called out as its distinguishing feature (plan:129). A phone cannot hold a request open for a full agent turn anyway, so liveness comes from the SSE stream and the response is the final state. If the client disconnects, the handler abandons its wait on `r.Context().Done()`; the run continues, because the detached context above is what guarantees it.

### How the stream ends

There are exactly three ends, and the spec now says which:

1. **The client disconnects.** `r.Context()` is done, the handler returns, `Subscription.Close` runs (DoD 6). No frame is written — the client is the one who left.
2. **The byte bound is exceeded.** The subscriber receives the terminal frame: `event: session.error`, `data: {"error":{…}}`, `data: [DONE]`, then close. This is the only `[DONE]` serve-4 emits deliberately, and it means *this stream ended for a reason you must notice*, not *a turn finished*.
3. **The server stops.** `cmd/wopr/serve.go:138-147` calls `srv.Serve(ln)` with no signal handling, no `srv.Shutdown` and no `Host.Shutdown`. There is no code path here, so this end is documented, not implemented, and building one is a separate slice.

A **per-turn** `[DONE]` is wrong and is not what the plan asks for. `/global/event` is one stream for **all** sessions (plan:121); a per-turn sentinel would make the app tear down and rebuild the stream on every turn, and `Last-Event-ID` replay does not exist (plan:162-163) so there would be nothing to resume from. A **bounded stream lifetime** is worse: it manufactures a reconnect on a timer, and the reconnect is the app's most expensive operation.

`TestServeFanoutDropsStalledSubscribers` reaches end 2. The topology test in §Q4 reaches end 1 by cancelling its request context once the reconciliation burst arrives — a live reader that hangs would otherwise run to `go test`'s 10-minute panic.

### The forwarder

`Host` builds a bus (`host.go:36`) and `Bus.Publish` has exactly one caller in the tree, a test (`host_test.go:209`). Nothing drains `Session.Events()` on the serve path. `Host.Start` gains one goroutine per session: `for ev := range sess.Events()`, `if coding.AcknowledgeEvent(ev) { continue }`, then the translator, then `h.bus.Publish`.

`AcknowledgeEvent` stays, and the reason is narrower than "mandatory or something deadlocks". `FlushEvents` (`coding/session_event_barrier.go:23-43`) is called only from `RunAgentPrompt` (`coding/session.go:749`, `:758`) and RPC's `settlePrompt` (`rpc.go:551`) — **not** from `sendContent` (`:652-699` contains no `FlushEvents`), which is the path serve-4 uses. So no barrier reaches the forwarder today. It acknowledges anyway: it is the only `Events()` consumer, one line, and a barrier that nobody acknowledges is a permanent block for the next caller that reaches one.

`Session.Subscribe` (`coding/session.go:1648`) is the alternative serve-1 pointed at (`BACKLOG.md:81-82`) and serve-4 does **not** take it. Its listeners run synchronously **before** the event reaches `Events()` (`coding/session.go:1645-1647`), which puts the whole fan-out on the agent goroutine, and its own doc warns that "a listener must not wait for a Session operation that synchronously emits another event". A goroutine draining `Events()` keeps the fan-out off the agent's path and adds no second subscription mechanism.

**Single-consumer invariant.** `Session.Events()` is one channel (`coding/session.go:769`). Today `ServeRPC` drains it (`rpc.go:566`) with a session it built itself (`cmd/wopr/rpc_mode.go:207`), so there is no overlap. serve-4 must not change that: a host-owned session is never passed to `ServeRPC`, or the two drains split the event stream. That belongs in a comment on the forwarder, because it is invisible and the failure is silent message loss.

## Q4 — message topology

This is the risk the plan names (plan:354-356), and it does not resolve the way the plan assumes.

**The constraint.** `messageDTO.ID` is the transcript entry ID (`serve_handlers.go:689`), and entry IDs are 16 hex chars from 8 random bytes generated at append time (`internal/codingagent/session.go:973-977`). The agent's `MessageStartEvent`, `MessageUpdateEvent` and `MessageEndEvent` carry an `AgentMessage` and **no ID** (`agent/agent.go:275-285`). Persistence happens at `message_end`, driven by `OnMessagePersist` (`agent/agent.go:563-572`, `:1080-1097`, wired at `coding/session.go:429-434`), which `coding/session.go:673-676` states is the single persistence site. And `agent.emit` persists **before** it sends the event to the channel (`agent/agent.go:1166-1174`), so by the time any listener sees `MessageEndEvent`, the entry is already on disk.

So the transcript ID does not exist yet while the deltas are being produced, and **no Go-side seam makes it exist earlier**. opencode does not have this problem because it allocates the message row before streaming. Chasing a way to inject an ID into `AppendMessage` would mean changing the persistence site for every mode to serve one transport.

### The provisional ID

`TurnStartEvent.TurnIndex` cannot be used. `agent_loop.go:89` emits `TurnStartEvent{TurnIndex: 0}` at the head of **every run**, the per-turn emission at `agent_loop.go:151` fires only from the second turn on, and `loopRun.turnIndex` (`:60`) is zero-valued per run and incremented at `:362`. So `TurnIndex` is unique *within a run* and restarts at 0 for every prompt — `msg_<sessionID>-<turnIndex>` would put every prompt's first assistant turn under `msg_<S>-0`. There is no other per-turn key in `agent/`: `TurnStartEvent.Timestamp` is wall-clock and is not an identity.

The counter is incremented at **`MessageStartEvent`**, not at turn start, and that is the whole fix:

Five sites, all of them:
- `agent_loop.go:93` — the run's replayed prompt messages.
- `agent_loop.go:322` — anything appended mid-loop (steering, follow-up, tool declarations).
- `agent_loop.go:444` — `requestError`, paired with its `MessageEndEvent` at `:445`. A provider failure that never reaches `consumeStream` lands here, so it counts.
- `agent/agent.go:1220` (`ai.StartEvent`) with the `:1209-1213` fallback at `:1211` — the assistant.
- `agent/agent.go:1145` — `catchRunFailure`'s failure path.

`coding/session.go:1775-1779` also sends a `QueueUpdateEvent` on a `MessageStartEvent`, **in addition to** it and never instead: the branch calls `consumeQueuedMessage` (`:1244-1271`) and `sendEvent`s the `QueueUpdateEvent` it returns, then falls through to `sendEvent(ev)` at `:1800` with the `MessageStartEvent` unchanged. So a counter keyed on `MessageStartEvent` sees every start, and `QueueUpdateEvent` is not a sixth site.

Every message emits **exactly one** `MessageStartEvent` before its updates and its `MessageEndEvent`. So one host-owned counter per session yields `msg_<sessionID>-<n>`, stable for the whole message, unique across every prompt in the session's life, and **it answers the role question for free**: the user message gets `msg_<S>-k` and the assistant gets `msg_<S>-k+1`, which is why `MessageEndEvent` needs no filter to keep the two apart. The counter lives in the serve translator's per-session state, not in `agent/`, and needs no atomic: the forwarder for a session is one goroutine, and the translator is called only from it.

### The reconciliation — and the blocker the findings missed

`TurnEndEvent` carries `MessageEntryID` and `ToolResultEntryIDs` (`agent/agent.go:268-274`), populated by `turnEndWithEntryIDs` (`coding/session.go:574-581`). **Those fields never reach `Session.Events()`.** The population happens in the `OnEvent` hook at `coding/session.go:420-428`, which reassigns its own local `ev` and passes it to `observeRouteTiming`; `agent.emit` then sends the **original** `ev` to `EventCh` (`agent/agent.go:1156-1174`), because `OnEvent` takes its argument by value. And `observeRouteTiming` (`coding/session_router.go:716-736`) switches on `MessageUpdateEvent` and `MessageEndEvent` only — it discards `TurnEndEvent` entirely, so the enriched copy is computed and dropped on the floor. A forwarder draining `Events()` therefore sees `TurnEndEvent` with an empty `MessageEntryID`, and the whole provisional-ID reconciliation as previously written has **no source**.

The fix is the smallest one that reuses the resolver that already exists. `findPersistedMessageEntryID` (`coding/session_recovery.go:95-147`) is the one correct implementation: an identity-keyed index (`entryIDsByMessage`) with a projection walk for messages the index has not seen, and it knows about compaction and context edits. Re-deriving it in `serve` — matching "the newest assistant entry" from a transcript tail — would be ~30 lines that are wrong the first time a context edit lands between the message and the tail read. So `coding` gains one exported method, `(*Session).MessageEntryID(agent.AgentMessage) (string, bool)`, a four-line wrapper with no behaviour change, and `coding/host` is the layer that calls it — which is exactly what that layer is for. `serve` still does not import `coding`.

The reconciliation therefore triggers at **`MessageEndEvent`**, not `TurnEndEvent`, because that is the event whose message is already persisted and whose `Assistant.Content` is already final:

- resolve `MessageEntryID` for the assistant message;
- emit `message.updated` with the real ID;
- emit one `message.part.updated` per block, with `partID(realEntryID, kind, contentIndex)`.

That is strictly better than a turn-end trigger: it lands one event earlier, it covers the failure path at `agent/agent.go:1145-1148`, and it needs no `TurnEndEvent` handling at all.

**The part-ID helper, shared — and pinned to which index.**

```go
// partID is the single source of part identity. The SSE mapper and
// entriesToMessages both call it, so a streamed part ID and a transcript
// part ID cannot drift.
func partID(messageID, kind string, index int, callID string) string
```

- text → `<msg>-text-<index>`
- reasoning → `<msg>-reasoning-<index>`
- file → `<msg>-image-<index>` — **transcript-only**, see below
- tool → `<msg>-tool-<callID>`

**Which forms are shared, and which are transcript-only.** `text`, `reasoning` and `tool` are shared by both sides and are the ones the index-alignment claim is about. `file` is **transcript-only**: `ai.ImageContent` does not implement `isAssistantContentBlock()` — `ai/messages.go:71-74` implements it for `TextContent`, `ThinkingContent`, `ToolCall` and `ServerToolContent`, and `ImageContent` implements only `isToolResultMessageContent()` (`:83`). An assistant message's `Content` is `[]ai.AssistantContentBlock`, so an `ImageContent` can never appear in one, and no `ai.*Event` carries an assistant image. `-image-<index>` is therefore reachable only on user and toolResult messages (`serve_handlers.go:713-732`), which the SSE mapper never emits — the mapper publishes assistant messages only (§Q3's role filter). The form lives in the shared helper so the transcript cannot invent a third spelling; there is no stream counterpart to hunt for, and DoD 8's index alignment is stated over the three forms that actually have both sides.

**Sharing the helper is necessary and not sufficient**, which is the honest version of DoD 8. `<index>` is the index into the **full content slice, enumerated before any filtering**, and both sides must agree on that. The stream side gets it free from `ai.TextDeltaEvent.ContentIndex`, `ThinkingDeltaEvent.ContentIndex` and `ToolCallEndEvent.ContentIndex` — indices into `partial.Content`. The transcript side today iterates `for _, block := range content` with no index (`serve_handlers.go:695`) and emits `e.Base.ID + "-text"` (`:699`), `+ "-reasoning"` (`:707`) and `+ "-image"` (`:726`), so an assistant message with two text blocks produces two parts with the same ID. Changing that loop to `for i, block := range content` and threading `i` fixes the duplicate. And because `entriesToMessages` has **no case for `ai.ServerToolContent`** (`:696-749`), while `ai/stream_builder.go:336` does produce it, enumerating before filtering is what keeps the indices aligned: for `[ServerToolContent, TextContent]` the stream says `-text-1` and, with `i` from the full slice, the transcript says `-text-1` too. Counting only mapped blocks would say `-text-0`. That is the specific drift DoD 8 forbids, and the tool form `+ "-tool-" + callID` (`:736`) stays byte-identical.

**The statement of stability, truthfully.** The final burst and the persisted transcript agree **by construction on IDs**: both are `partID(<the same entry ID>, kind, <the same full-slice index>)`. The deltas within a turn carry the provisional ID. A shared helper plus a pinned index is what makes "cannot drift" true; the helper alone is not.

## Q5 — `model`, and the carried debt

**Decision: serve-4 applies `model` and ships the one-line `appendSessionLine` separator fix. This retires serve-3 carried-debt item 1.**

The claim that serve-4 "adds no caller in that blast radius" was false, and it was self-contradicted inside the same spec: `model` was marked applied via `SetModel`, whose path is `setModel` (`coding/session.go:839-862`) → `s.inner.AppendModelSwitch` (`:849`) → `appendOnLeaf` (`internal/codingagent/session.go:712-717`, `:621-635`) → `AppendEntry` (`:484`) → `appendSessionLine` (`:567-577`) — the exact unfixed function, and serve-4 would be a **new** serve-owned caller in it, not one of the seven serve-3 already recorded (`BACKLOG.md:226-231`).

The alternative is to accept-and-ignore `model`. That makes the app's model picker silently do nothing: the client sends `POST /message {"model": …}` and gets a 200 that changed nothing. A 200 that lies is worse than a 400.

**The defect, and the fix.** `appendSessionLine` opens `O_APPEND|O_CREATE|O_WRONLY` and writes `"%s\n"` without checking whether the file's last line was terminated. On a file that does not end in a newline — an imported session, an interrupted write — the new record is glued onto the truncated one and **both** records are destroyed. `appendJSONLine` (`internal/codingagent/session_manager.go:374-392`, with the `Fprintf` and `return` at `:390-391`) already implements the correct behaviour: open `O_APPEND|O_RDWR`, read the last byte, write `'\n'` first if it is not one. It is in the same package, already measured by serve-3's single-revert harness (`BACKLOG.md:266-269`), and serve-3's own doc comment says why: "an imported or interrupted session would otherwise have the new record glued onto the truncated one, destroying both."

So the fix is `appendSessionLine` opening `O_RDWR` and delegating to `appendJSONLine`. Two lines, no new function, no new file, and the record stream can only ever gain one byte — never lose or reorder one. Two things **are** given up, and neither is behaviour anyone depends on:

- **The error wrapping.** `appendSessionLine` currently wraps its two failures as `"session: open for append: %w"` and `"session: append write: %w"` (`internal/codingagent/session.go:570`, `:574`); delegating drops both wrappers. Nothing asserts on those strings — a repo-wide grep for both returns only the two `fmt.Errorf` sites themselves, no test and no caller matching on them — and the underlying `*os.PathError` survives either way, so the failure is still diagnosable from its path and errno.
- **Two syscalls per append.** `appendJSONLine` does one `f.Stat()` (`session_manager.go:375`) and, only when the file is non-empty, one `ReadAt` of the last byte (`:381`). Every `AppendEntry` now pays both. On `O_APPEND|O_RDWR` the `ReadAt` is a positional read that does not disturb the append offset, and the cost is two syscalls against a file open that already costs three — but it is not free, and the claim is two extra calls, not "no change". AGENTS.md's rule is explicit: "Fix the root cause. When a function is wrong, fix it once where every caller routes through." `appendSessionLine` is the root; fixing it once retires the defect for all seven recorded callers plus serve-4's new one. It does not touch `internal/codingagent/session_manager.go` beyond calling a function that already lives there, so the retention freeze at `BACKLOG.md:17-20` — `raw` is write-critical and `loadSessionFile` must not change — is untouched.

**The risk being taken, stated.** The risk is a write path with no dedicated harness. I am taking it because the alternative takes a larger one: a documented endpoint that accepts a field and silently discards it, on a feature the client ships a picker for. The write-path risk is bounded in three ways the code supports: the fix is the already-audited helper in the same package, not new logic; it is purely additive at the byte level, so it cannot drop or reorder a record; and it is exercised by the measurement serve-3 already recorded for that helper. **Cost: this is file #5 in the list, and it is the reason the list is not nine.**

`BACKLOG.md:230` records the function as `session.go:567-577` with no package prefix — an unqualified filename, not a wrong package. The conclusion that it lives in `internal/codingagent` rather than `coding` is independently correct from the tree. The BACKLOG edits are main-checkout work; see §Out of scope.

## Q6 — order of work

`BACKLOG.md:481` says "Do not start SSE before a prompt streams correctly — message topology is the real risk here". No gate command inspects commit order and both files exist in the final tree, so this is deliberately **not** a DoD item — an unenforceable line in a done-list is worse than no line. It is a build sequence and it is the point. serve-4 is built in this order, each step green on its own:

1. `bus.go`'s bounded queue, `host.go`'s `PromptContent`/`PromptContentWait` and owned cancel, and the three prompt handlers with their status codes and the body cap. **Green before any SSE code exists.** If nothing here works, no stream can be blamed for it.
2. The part-ID helper, the transcript-side index fix, and `messageDTO` → `{info, parts}`. This is the message-topology risk and it is testable with no stream at all.
3. `coding`'s `MessageEntryID` wrapper and `host`'s translator seam and forwarder, proven by a unit test that feeds a `*host.Session` events and reads the bus — no HTTP involved.
4. `serve_sse.go`: the mapper, then the handler, then the connection cap.
5. The `appendSessionLine` fix, which is independent of all of the above and ships with the `model` decision it unblocks.
6. Tests and benchmarks alongside each step, not at the end.
7. The two `BACKLOG.md` edits, in `/home/kc/dev/wopr`, after the merge.

## Risks

- **Provisional message IDs** (§Q4, Open question 1) — the only design risk in the slice that cannot be closed from Go code. Mitigation: the literal-ID reconciliation test, plus the manual app gate.
- **The `r.Context()` trap** (§Q2) — invisible, and it makes `prompt_async` a no-op that still answers 204. Mitigation: the detached context is a stated invariant on the two new methods, not an implementation detail.
- **`AppendModelSwitch` failing inside `SetModel`** (§Q5) — `setModel` returns an error if the audit append fails, but it has already stored the new model (`coding/session.go:844-851`). serve-4 answers 500 on that error while the session's model has changed. Honest and rare; recorded rather than papered over.
- **The translator and `AcknowledgeEvent`** (§Q3) — a listener that never acknowledges is a permanent block for a future caller. Not on serve-4's critical path (`sendContent` never calls `FlushEvents`), which is exactly why it is easy to forget. Mitigation: named in the forwarder's comment.
- **Events split across two drains** — `Session.Events()` has one consumer (`coding/session.go:769`). Today `ServeRPC` and the host hold different sessions (`cmd/wopr/rpc_mode.go:207`). Mitigation: comment on the forwarder; no test, since the invariant is currently true by construction and a test would only guard a caller that does not exist.
- **Lint disposition, stated once.** `errcheck` is **not** excluded anywhere in `.golangci.yml` (only `gosec` G104 is, `:104-105`), so every `w.Write` needs a disposition: the SSE write is `if _, err := w.Write(frame); err != nil { return }` — one site, and a write error is the only signal that the connection is gone, so it ends the handler. `gocritic`'s `singleCaseSwitch` and `ifElseChain` are enabled (`:19`), so no `switch` with one case and no `if`/`else if` chain longer than two branches; the repo's surviving chains are two-branch. `go fix -diff ./...` must stay empty, so any `sync.WaitGroup` use is `wg.Go(func(){…})` and never `wg.Add(1)` + `defer wg.Done()` (`host_test.go:136,151,165,202` is the local idiom). No symbol is exported to satisfy `unused`, unlike serve-1's deliberate case (`bus.go:16-18`). And there is **no configured size or complexity ceiling**: `lll`, `funlen`, `gocyclo`, `cyclop`, `nestif` and `revive` are all disabled, so nothing in this spec should be justified by a size limit.
- **Test hermeticity** — a real prompt needs `WOPR_TEST_FAUX=1`, because `BuildModel` refuses `test-faux` without it (`coding/model.go:161-166`), which means `cmd/wopr/serve.go:135`'s `test-faux/faux-1` fallback cannot start a session unless that variable is set — and when it is unset the failure is a `BuildModel` error, not `ErrNoModel`, so `createSession` answers **500** rather than the 409 it uses for a missing model (`serve_handlers.go:210-217`). The serve tests therefore set it explicitly with `t.Setenv` (no `t.Parallel` in those tests), and the existing `TestMain` hermetic setup (`serve_test.go:22-59`) already clears `ai.ProviderCredentialEnvVars` and points `WOPR_HOME` at a temp dir. The faux provider is in-process (`coding/services.go:121-123`), so no network and no credential is involved. **A real send is reachable** and hermetic: `host_test.go:138,152,166` already drive `Host.Prompt` end to end against a loopback `httptest` provider (`:69`), and the faux provider scripts the three shapes serve-4 needs — `Run: expr 20 + 22` for a tool call (`ai/test_faux.go:312`), `TUI_LIVE_STREAM` for 24 deltas at 40ms (`:131-146`), and a provider failure for the `session.error` path (`:147-154`). No benchmark needs a live provider; no test needs tmux.
